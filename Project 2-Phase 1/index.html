Foundations

What LangChain is, and what a chain does

LangChain is a framework for building LLM apps without hand-wiring the same plumbing every time — sending a prompt, calling a model, reading back the response, remembering earlier turns, reaching for outside tools. It gives each of those a standard shape so they snap together.

A chain is the simplest way to snap them together: a fixed sequence of steps where each step's output becomes the next step's input. The order is decided when you write the app, not while it runs. Most LLM features start as one of these.

02

The first and last link

Prompt templates and output parsers

A prompt template is a prompt with blanks in it. You write the wording once, then fill in the blanks at runtime — so prompt wording lives in one place instead of being rebuilt with string concatenation all over the codebase.

An output parser does the opposite job: the model always replies in plain text, so the parser turns that text into something the rest of the program can actually use — a list, a JSON object, a specific data class — and can flag it if the model didn't follow the format.

example.py 
from langchain.prompts import PromptTemplate
from langchain.output_parsers import CommaSeparatedListOutputParser

template = PromptTemplate.from_template(
    "List 3 {topic} in a short comma separated list."
)
parser = CommaSeparatedListOutputParser()

prompt = template.format(topic="LangChain use cases")
# -> "List 3 LangChain use cases in a short comma separated list."

raw_output = "chatbots, document QA, data extraction"
parsed = parser.parse(raw_output)
# -> ['chatbots', 'document QA', 'data extraction']
03

Making a chain feel less stateless

Memory and tool calling

On its own, an LLM call is stateless — it has no idea what was said one message ago unless you put it back in the prompt yourself. These two features are how LangChain apps get past that.

Memory

Carries earlier turns of a conversation forward so the model can refer back to them. A buffer memory just replays the raw history; a summary memory compresses older turns so long conversations don't blow the context window.

Tool calling

Lets the model ask the app to run something outside itself — a search, a calculator, a database query — mid-answer. The model outputs "call this tool with these arguments," the app runs it, and the result gets fed back so the model can use it.

04

When a straight line isn't enough

What LangGraph is, and chain vs. agent

LangGraph is a library, built to work with LangChain, for laying an app out as a graph of steps instead of a single line. A graph can loop back, branch into different paths, or revisit a step — things a straight chain structurally can't do.

That maps onto a real distinction: a chain follows a path fixed at build time; an agent is an LLM deciding, while it runs, which step or tool comes next.

ChainAgent
Step order Fixed when you write it Decided by the model at runtime
Can it loop / branch? No — always A → B → C Yes — can revisit or skip steps
Predictability High Lower, but more flexible
Good fit for Well-defined, repeatable tasks Open-ended tasks with several possible paths

The vocabulary of a graph

Core LangGraph concepts

Node

One unit of work — a function, an LLM call, or a tool call. Each node reads the current state, does something, and returns an update.

Edge

A connection saying which node runs after which. Plain edges always point the same way, every run.

State

A shared object passed between nodes — the graph's working memory. Every node can read it and hand back changes to it.

Conditional edge

An edge whose destination is picked at runtime by a function that inspects the state — this is where branching and looping actually happen.

Why this matters for the next project

The orchestrator agent

An orchestrator agent sits at the top of the graph. It doesn't do the specialised work itself — it looks at the task, breaks it into subtasks, routes each one to the node or agent built for that job, and combines what comes back.

The upcoming project needs one because it isn't one job, it's several: research, writing, formatting — each better handled by a focused node than by one generalist trying to do everything. An orchestrator keeps that routing in a single, visible place (its conditional edges), which means a new specialist can be added later without rewriting the rest of the graph.
